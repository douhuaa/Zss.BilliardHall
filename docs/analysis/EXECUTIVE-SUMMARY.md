## 🎯 核心结论

### 问题重述

> "如何把强类型测试规约系统（Specification）替换现有 Markdown 文档（ADR）为主导的系统？"

### 答案

**不应该"替换"，而应该"重新定位"**

当前系统已经是一个高度成熟的**混合架构治理体系**，两个系统互补而非冲突：

```
当前现实：
┌──────────────┐        ┌──────────────┐
│   ADR 文档    │ ◄────► │   RuleSet    │
│  (46个)      │        │   (43个)     │
│  93.5%覆盖   │        │   手工同步   │
└──────────────┘        └──────────────┘
       ▲                       ▲
       │                       │
   Agent/Skills 主要读 ADR     测试体系部分使用

建议未来：
        ┌─────────────────┐
        │   RuleSet       │
        │ (唯一真相源)    │  ◄─── 所有规则定义在此
        └────────┬────────┘
                 │
     ┌───────────┼───────────┬──────────┐
     ▼           ▼           ▼          ▼
  ┌─────┐   ┌──────┐   ┌────────┐  ┌──────┐
  │ ADR │   │ 测试  │   │ Agent  │  │ CI   │
  │文档 │   │ 生成  │   │ 指令   │  │ 检查 │
  └─────┘   └──────┘   └────────┘  └──────┘
  (派生)    (自动)      (基于API)   (自动)
```

## 💡 推荐方案

### 核心策略

**"重新定位系统角色"** 而非替换：

1. **RuleSet** = 唯一真相源
   - 所有架构规则的权威定义
   - 强类型、可查询、可验证
   - 版本控制友好

2. **ADR 文档** = 人类可读说明
   - 保留 Context、Rationale、Consequences
   - Decision 章节从 RuleSet 自动生成
   - 仍是架构决策的沟通媒介

3. **测试** = 自动化执法
   - 从 RuleSet 自动生成测试框架
   - 200-300 个新测试方法
   - 确保每个规则可验证

4. **Agent/Skills** = 基于 API 工作
   - 查询 RuleSetRegistry 获取规则
   - 基于结构化数据生成代码
   - 失败信息引用精确 RuleId

### 实施路径（7阶段）

```
阶段1: 补充基础        (1-2天)  ✅ 分析完成
阶段2: 构建生成工具    (2-3天)  ← 核心工具
阶段3: 更新Agent/Skills(3-4天)  ← 关键整合
阶段4: 生成测试套件    (3-4天)
阶段5: 重新生成文档    (2-3天)
阶段6: CI/CD集成      (2天)
阶段7: 验证清理       (2-3天)

总计: 18-24 工作日
```
